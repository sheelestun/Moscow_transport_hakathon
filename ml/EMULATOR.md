# Эмулятор NDTP и ML-модуль: что проверено

Проверено 26.09.2026 на образе `ndtp-telemetry-emulator:1.0`: эмулятор → собственный приёмник NDTP
(разбор NPL/NPH/`G6CellNav00` по спецификации, CRC-16/Modbus) → ML-сервис в Docker.

## Как жюри проверяет ML

| Критерий | Где проверяется | Что нужно от ML |
|---|---|---|
| 1. Точность (0–6) | автоматически по `submission.csv` | сделано: оценка score ≈ 1.0 (MAE 39.8 на test при бейзлайне 93.4) |
| 2. Горизонт 10–15 мин (0–4) | **на потоке**, а не по выгрузке | в каждом ответе `lead_min` и `horizon_ok`; алерт до события, с прогнозом и причиной |
| 3. Система в Docker (0–6) | поток → прогноз → дашборд | `docker compose up ml`, `/predict` по контракту, Swagger `/docs` |
| 5. Скорость и надёжность (0–4) | замеры + обрывы связи | `PERFORMANCE.md`: p50 44 мс, холодный старт 2.2 с, деградация без падений |

**Точность на эмуляторе проверить нельзя:** у его потока нет фактического расписания. Поэтому на потоке важны не
секунды MAE, а то, что система работает, соблюдает горизонт и не выдаёт уверенную чушь на странных данных.

## Что шлёт эмулятор

- `autoGenerate: true` — **случайное блуждание** около Москвы (у нас 55.79, 37.59, скорость 37–53 км/ч).
  С маршрутами не связано: ML видит ТС в километрах от своих остановок.
- Время в пакете (`timestamp`) — **текущее UTC**, а не 6 января 2026 (дата датасета).
- Явные координаты работают, но поля ячейки надо класть **внутрь `"fields"`**:
  ```json
  {"type": "G6CellNav00", "fields": {"latitude": 556685750, "longitude": 374447400,
   "extraDopBit5": true, "extraDopBit6": true, "extraDopBit7": true, "speedAvg": 45, "course": 225}}
  ```
  Поля на верхнем уровне ячейки эмулятор молча отбрасывает и шлёт нули с `valid = false`.
- Каждый `POST /api/config` — переподключение и новое рукопожатие на каждое устройство (backend должен это спокойно
  принимать; по спецификации переподключение и так штатное).

## Живое демо на настоящих треках: `infra/emulator_replay.py`

Раз в N секунд перезаливает конфиг эмулятора координатами 13 реальных ТС из `validate/traffic.csv` на текущий момент
«датасетного» времени. Проверено 45 с: 12 из 13 ТС шлют координаты (13-й в это время суток не ездит), точки лежат в
1–250 м от своих остановок, ML на этом потоке отвечает `data_status: live`, `horizon_ok: true`.

```bash
docker load -i dataset/ndtp-telemetry-emulator.tar
docker run --rm -p 18080:18080 --add-host=host.docker.internal:host-gateway --name ndtp-emu ndtp-telemetry-emulator:1.0
python infra/emulator_replay.py --dataset ./dataset --target-host host.docker.internal --target-port 9201
```

Сопоставление для backend (скрипт пишет его в `emulator_clock.json`):

- `unitId` пакета = `unit_id` из `traffic.csv` → `tr_id`;
- датасетное время = `dataset_start + (UTC пакета − wall_start_utc) × speed`; при `--speed 1` и старте «сейчас» это
  просто «UTC → МСК (+3 ч), дата → 2026-01-06»;
- для каждого ТС запрос к ML — только если в плане есть остановка в окне (T+10, T+15] мин.

**Холодный старт истории.** GPS-признакам нужна телеметрия за последний час (прибытия на пройденные остановки,
скорость за 15 мин). Первые минуты после запуска потока прогноз опирается в основном на план и `cur_dev_s`
(backend считает её по своим прибытиям). Чтобы не ждать час, backend может предзагрузить буфер ТС из `traffic.csv`
за час до старта — это те же данные, что уйдут и через эмулятор.

## Подсказка `cur_dev_s` на потоке и режим `gps`

Проверено по train/test (совпадение 100%): в датасете `cur_dev_s` = (факт − план) на **последней остановке ТС,
плановое время которой <= T**. Факт этой остановки у ~45% точек наступает **после** T (в среднем через 2 мин,
до 10 мин): официальная подсказка частично «из будущего». На потоке так посчитать нельзя.

Backend на потоке считает подсказку честно — **задержка на последнем прибытии, найденном по GPS**
(`backend/app/state/fleet.py`, тем же правилом, что наш `features.tabular.gps_history`), нет прибытий → 0.
Модель, обученная на официальной подсказке, на такой ошибается сильнее, поэтому для потока обучен отдельный
комплект `catboost_gps_*` (`train_catboost.py --gps`): там подсказка — это `gps_last_dev` (только телеметрия,
никаких фактов расписания). В режиме `gps` сервис сам пересчитывает подсказку по присланной телеметрии тем же
правилом — результат не зависит от мелких расхождений в реализации backend'а.

Проверка на test (MAE, с):

| Вариант | MAE |
|---|---|
| основная модель, официальная подсказка (сабмит) | 39.8 |
| **основная модель, GPS-подсказка — так было на сервере до 27.09** | **66.8** |
| **gps-модель, GPS-подсказка — так на сервере после выкатки** | **45.3** |
| бейзлайн: GPS-подсказка как прогноз | 125.1 |

Интервал gps-модели накрывает 80% фактов, AUC вероятности опоздания 0.970. Включается переменной
`ML_DEFAULT_CUR_DEV_MODE=gps` (или полем `cur_dev_mode` в запросе); сабмит по-прежнему делает основная модель.
Альтернативный сабмит только по телеметрии — `submission_gps.csv` (`train_catboost.py --gps --fit`).

## Как ML ведёт себя на данных эмулятора

| Поток | Ответ ML |
|---|---|
| Настоящие треки через `emulator_replay.py` | `live`, до маршрута 1–250 м, `horizon_ok: true` |
| `autoGenerate` (случайное блуждание) | 200, `data_status: off_route` (ТС в 3+ км от своих остановок), `confidence` ×0.5, первая причина — «ТС в N км от своих остановок: прогноз опирается на расписание и последнее отклонение» |
| Нет пакетов / все координаты невалидны | 200, `no_telemetry`, прогноз по плану и `cur_dev_s` |
| Пакеты позже T | отбрасываются сервисом |

Порог `off_route` — 3 км: так далеко от своих остановок (план ±1 ч) бывают ~4% реальных точек (стоянка в парке перед
рейсом), на них модель обучена, поэтому прогноз не меняется — только флаг и сниженная уверенность.
